## 2. 项目目标

建设一套面向消费者和商户运营人员的生活服务平台，支持商户信息浏览、消费者评分/评价、评价点赞与分析、优惠券活动发布及限时抢购。秒杀链路需要在高并发下限制库存、保证每个活动每位用户最多购买一张，并通过异步处理降低主链路压力。

### 2.1 本期建议范围

- 消费者：注册/登录、商户查询、查看评价及评价摘要、发布/管理自己的评价、浏览优惠券、参与秒杀、余额支付、查看订单。
- 商户/运营：维护商户资料、创建和管理优惠券活动、查看活动及订单数据。
- 系统：缓存热点数据、排队处理秒杀请求、处理失败重试与数据核对、维护余额账本并为外部支付渠道预留扩展点。

外部支付渠道、充值、退款、配送、复杂推荐和 AI 评价理解不在首期实现范围。首期设计余额账本和支付扩展点；是否付费购买优惠券、是否需要退款需业务确认。

## 3. 用户角色与核心场景

| 角色 | 主要操作 |
| --- | --- |
| 消费者 | 搜索商户、浏览评价和优惠券、参与秒杀、查看抢购结果 |
| 商户运营 | 维护商户资料、发布和管理优惠券、查看活动情况 |
| 平台管理员 | 管理账号与内容、处理违规信息、查看系统运行情况 |

### 3.1 秒杀场景

1. 运营人员创建活动，配置库存、活动时间和有效期；每个活动固定每位用户最多购买一张。
2. 活动开始前将活动信息和库存预热到 Redis；活动信息使用逻辑过期等方式维持热点数据可用。
3. 用户提交抢购请求，服务端校验登录态和活动状态，再调用 Redis Lua 脚本原子校验活动时间、库存和用户购买资格。
4. 通过校验的请求进入异步处理队列，接口返回“请求已受理/处理中”，客户端查询最终结果。
5. 消费者幂等处理请求，在 MySQL 事务中将可售库存转为预留库存并创建待支付订单；数据库唯一约束和条件更新作为最终防重、限量保障。
6. 付费券用户在支付期限内使用账户余额支付；余额不足时订单保留待支付状态至超时，超时关闭订单并释放库存。免费券跳过扣款。失败请求进入重试或死信处理，并通过补偿/核对任务修复 Redis 预扣库存与数据库结果之间的差异。

### 3.2 消费者评价场景

1. 消费者在商户详情页提交评分和评价内容，可查看、编辑或删除本人评价（具体可编辑时限待定）。
2. 服务端校验登录状态、内容格式和评价权限，必要时进入审核流程。
3. 评价写入 MySQL 后删除商户评价摘要缓存；统计任务更新评分分布、评价数量等摘要。
4. 用户可以对评价点赞/取消点赞；同一用户对同一条评价只计一个有效赞，重复请求保持幂等。是否必须关联已完成订单、每个用户对同一商户可评价次数及审核规则待确认。

## 4. 总体架构

```text
消费者 H5 / 运营管理 Web
   │ HTTPS
   ▼
Spring Boot API 服务
   ├── 账号与权限模块
   ├── 商户与评价模块 ───── MySQL
   ├── 优惠券与秒杀模块 ─── Redis（Lua、缓存、限流）
   ├── 订单模块 ────────── 消息队列 ── 秒杀消费者
   └── 管理与运营模块             │
                                  └── MySQL（订单、库存、消息记录）
```

建议先采用模块化单体，按业务边界划分模块，避免首期引入微服务的运维复杂度。秒杀消费者可独立部署或单独扩容。消息队列建议首选 RocketMQ，原因和前提见 6.3；如果团队已有成熟的 RabbitMQ 运维能力，可优先沿用现有平台。

## 5. 功能模块设计

### 5.1 账号与权限

- 消费者、商户运营、平台管理员身份与角色管理。
- 需要登录的接口校验身份；运营接口按角色授权。
- 登录方式、账号注册方式及是否接入第三方身份服务待确认。

### 5.2 商户与评价

- 商户资料维护、分类/区域查询、关键词搜索、详情查看。
- 消费者对商户评分并发布、查询、编辑或删除本人评价；其他登录用户可对评价点赞/取消点赞。评价列表显示点赞数和当前用户是否已点赞。
- 点赞通过用户与评价的关系记录防重复；重复点赞/取消请求幂等。点赞数只在关系记录确实新增/删除时增减，并与点赞关系在同一数据库事务更新。评价统计包括评分分布、评价数量、点赞数等基础统计。
- 首期实现点赞/取消点赞；数据模型保留扩展评价举报、回复等互动的空间，是否加入首期由需求评审确定。
- 支持内容审核和举报处理的扩展点；是否“完成消费后才能评价”待确认。
- “评价分析”的分析维度、是否需要情感分析或 AI 摘要待确认；本稿仅按可解释的基础统计设计。

### 5.3 优惠券活动

- 活动创建、编辑、上下架、开始/结束时间及库存配置；每个活动每位用户最多购买一张。
- 活动详情和活动列表查询。
- 活动开始前预热 Redis；活动变更时更新数据库并删除相关缓存。

### 5.4 秒杀订单

- 秒杀资格原子校验、请求排队、订单生成、结果查询。
- 每位用户对每个活动最多一张；Redis 和数据库均以用户+活动维度防重，数据库 `campaign_id + user_id` 唯一约束作为最终保障，消费者按消息 ID/业务请求 ID 幂等。
- 订单状态至少包括“待支付、已支付、已关闭”；支付成功后按券种进入“待使用/待核销”。免费活动可跳过支付步骤。核销、取消和退款规则待确认。

### 5.5 账户与支付

- 消费者账户显示可用余额和余额变动明细；余额以 MySQL 账本为准，Redis 不作为资金账本。
- 使用余额支付订单；余额扣减、支付流水写入及订单状态变更在同一 MySQL 事务中完成，并使用条件更新防止并发超扣。
- 预留充值单、支付渠道适配层和微信支付 API 契约。首期不接微信、不创建真实充值成功记录；充值接口可暂不开放，或返回明确的“功能暂未开通”状态。
- 后续接微信支付时，服务端创建待支付充值单并请求微信预下单；支付结果以验签后的异步通知为准，并提供主动查单补偿。回调需验签、核对商户订单号/金额/币种、幂等入账。
- 充值金额以整数分存储；余额流水不可直接修改或删除，退款/冲正通过新的反向流水记录。

## 6. 关键技术设计

### 6.1 秒杀防超卖与一人一单

- Redis Lua 脚本在一次原子操作中检查活动状态、Redis 库存和用户是否已抢购；通过后预扣 Redis 库存并登记该用户的抢购资格。
- MySQL 事务中使用带库存条件的更新（可售库存大于零时转为已预留）并创建待支付订单；为活动/优惠券与用户组合建立唯一索引，抵御重复消息和并发重复请求。
- 用户余额支付时，在一个 MySQL 事务内校验订单仍待支付、扣减可用余额、写入不可变余额流水并将订单改为已支付。订单状态的条件更新和支付流水唯一键共同阻止重复扣款。
- 待支付订单设置明确的支付截止时间；超时任务与支付请求通过条件状态更新竞争，只有成功从“待支付”转换的事务能完成释放库存或扣款，避免过期和付款并发导致重复处理。
- 消费者处理成功后确认消息；处理失败按有限次数退避重试，超过上限进入死信队列并告警。
- Redis Lua 和数据库均按 `campaign_id + user_id` 控制活动限购一张，MySQL 唯一约束为最终防线。
- Redis 预扣与消息投递、MySQL 事务属于跨系统操作，不能仅靠单个数据库事务保证原子性。建议使用可靠消息投递（持久化消息、发布确认、消费幂等）并保存可追踪的抢购请求记录；配套超时补偿和定期库存核对。具体采用事务消息还是 Outbox 方案，需结合所选消息队列确定。
- 活动库存应有明确的初始化、预热、结束和对账流程；不能只依赖 Redis 中的库存值作为最终账本。

### 6.2 缓存设计

| 数据 | 缓存策略 | 失效/一致性处理 |
| --- | --- | --- |
| 商户详情、评价摘要 | Redis；本地缓存仅用于读多且允许短暂旧数据的热点 | 更新 MySQL 后删除 Redis，并广播/失效本地缓存；设置 TTL |
| 活动基本信息 | Redis + 可选本地缓存 | 变更时主动失效；高并发活动可使用逻辑过期并由后台刷新 |
| 秒杀库存/用户资格 | Redis 专用活动键，由 Lua 原子读写 | 活动结束或核对时重建/清理；与 MySQL 定期核对 |
| 不存在的商户/活动 | 短时空值缓存 | 设置较短 TTL，降低缓存穿透影响 |

通用缓存使用 Cache Aside：写请求先提交 MySQL，再删除 Redis 缓存；必要时延迟再次删除以缩小并发读写造成的旧值回填窗口。评价新增、编辑、删除或点赞状态改变后，删除受影响的评价列表/点赞数缓存。TTL 加随机抖动，避免大量键同时过期。延迟删除属于风险缓解措施，不是强一致性保证；热点数据的本地缓存还需有失效通知或足够短的 TTL。

### 6.3 异步队列与选型建议

- **建议首选 Apache RocketMQ**：本项目的核心消息是秒杀请求和订单状态任务，重点是可控重试、死信恢复和延迟任务，不是持续保留并反复分析的事件流。RocketMQ 官方能力包括事务消息、延迟/定时消息和消费失败重试；这些能力与秒杀订单创建、待支付订单超时关闭及失败恢复较贴合。事务消息可协调本地数据库事务和消息投递，但不能把 Redis Lua、MySQL 与 MQ 合并成一个原子事务，因此仍需请求记录/Outbox、消费者幂等和补偿对账。
- **吞吐目标**：RocketMQ 集群至少支持每秒 2,000 条秒杀/订单类消息的可靠发布与消费。该指标指 MQ 消息吞吐量，不自动等于整个 HTTP 秒杀链路的 2,000 QPS；后者还要结合 Redis、数据库事务和订单消费者单独压测。
- Kafka 更适合高吞吐事件流、长期保留和多消费者回放；对本项目首期的订单任务、逐条失败重试和延迟关闭任务而言，运维及消费模型可能偏重。
- RabbitMQ 也能通过持久化队列、发布确认、手动消费确认、重试和死信队列实现可靠订单任务，生态成熟且上手直接；但延迟任务的实现方式和运维能力需根据具体部署方案确认。如果团队已有 RabbitMQ 集群，沿用它通常比引入新中间件更合算。
- 因此本设计暂定 RocketMQ 为首选，但不是无条件要求；最终需看团队现有中间件、部署能力、目标峰值和可接受运维成本。选定具体版本后再核对对应版本的延迟消息范围、重试策略和 Spring Boot 集成方式。
- 秒杀 API 只在资格判断及可靠投递完成后返回受理结果，不等待完整订单创建。
- 消息携带请求 ID、用户 ID、活动 ID、创建时间等必要字段，不携带不必要的个人信息。
- 消费者先检查幂等记录，再在单个 MySQL 事务内完成库存扣减/预留、待支付订单创建和请求状态更新。
- 监控队列积压、消费延迟、重试数、死信数；提供人工查询和可重放机制，并确保重放不会产生重复订单。
- 订单待支付超时关闭可发延迟消息；同时保留定时扫描数据库的兜底任务，不能只依赖队列延迟消息完成资金/库存释放。

  选型依据可参考 [RocketMQ 事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)、[延迟消息](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/) 和 [消费重试/DLQ](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)。RabbitMQ 的可靠发布也需要生产者确认和消费者确认，可参考其[官方确认机制说明](https://www.rabbitmq.com/docs/confirms)。

### 6.4 余额与外部支付设计

- **账本模型**：`wallet_account` 保存可用余额（如需冻结资金再增加冻结余额）；`wallet_ledger` 记录充值、消费、退款和人工调整等每一笔变动。金额统一用整数分，避免浮点误差。
- **余额支付**：客户端提交订单支付请求和幂等请求号。服务端在数据库事务内锁定/条件更新账户余额、校验订单状态、插入唯一业务流水并更新订单状态；并发支付、重试或网络超时都不会重复扣款。
- **余额不足**：支付失败不扣款，订单仍可在支付期限内继续支付；超时后关闭订单并释放已预留库存。可用余额不足提示用户充值，但首期不提供真实充值能力。
- **免费与付费券**：活动价格为零时不产生余额扣款，订单按免费领取流程完成；付费券则在用户主动支付时从站内余额扣款。是否首期开放付费券由业务确认。
- **无充值渠道期间**：开发/测试环境可使用测试账户数据验证余额流程；生产环境没有真实资金来源前，不应开放余额充值或使用虚构支付结果，余额支付入口需按业务开关关闭。
- **充值预留**：后续 `POST /api/wallet/recharges` 创建 `PENDING` 充值单并返回支付渠道所需的调起参数；初期该能力处于关闭状态，不允许客户端直接增加余额。微信支付接入后，由服务端调用相应下单接口，接收并验证支付回调后才将充值流水入账。
- **微信支付适配**：将渠道能力封装在支付适配层，业务只依赖“创建支付、查询支付、验证通知”等统一能力。微信 API v3 回调需验签并解密；先核对订单和金额，再以数据库唯一约束幂等入账。若回调未到，后台按需主动查单补偿。接入细节遵循[微信支付 API v3 官方说明](https://pay.wechatpay.cn/doc/v3/merchant/4012081606)。
- **启用前置条件**：真实充值上线前需准备对应微信支付商户配置、回调域名与密钥管理，并确认充值面额、退款/撤销、对账及客服处理规则；用户端展示与下单方式（小程序、公众号、App、扫码等）决定采用的微信支付场景。
- **支付边界**：充值与订单余额支付是两段独立业务。微信零钱/银行卡支付不会自动成为站内余额；微信充值成功后先记入站内余额，用户再用站内余额支付订单。提现、转账、资金托管及退款渠道暂不纳入首期设计。

### 6.5 数据一致性

- MySQL 是商户、评价、活动、订单、余额账本及最终库存的持久化事实来源；Redis 用于加速查询及秒杀资格/库存控制。
- 订单创建、库存预留和消费请求状态应在同一个 MySQL 事务内提交；余额支付时，订单状态、余额账户、支付记录和余额流水也应在同一个 MySQL 事务内提交。
- 缓存删除失败时记录并重试；延迟二次删除使用可追踪任务，而非仅依赖进程内定时器。
- 建立活动库存对账：比较数据库剩余库存、成功订单数、处理中请求数和 Redis 预扣数量；发现差异时告警并按规则修复。

## 7. 数据模型草案

以下为逻辑实体，字段和拆表方式需在需求确认后细化。

| 实体 | 关键字段/约束 |
| --- | --- |
| user | id、状态、创建时间；账号标识需唯一 |
| merchant | id、名称、分类、区域、状态、评分摘要 |
| review | id、merchant_id、user_id、评分、内容、审核状态、点赞数、创建时间；可选关联 order_id |
| review_like | id、review_id、user_id、创建时间；review_id + user_id 唯一，保证同一用户对同一评价只计一个赞 |
| coupon_campaign | id、merchant_id、名称、总库存、活动时间、状态、每人限购（固定为 1）、售价（若活动为付费券） |
| coupon_order | id、request_id、campaign_id、user_id、订单金额、订单状态、支付截止时间、创建时间；campaign_id + user_id 唯一，保证活动每人最多一张 |
| seckill_request / outbox | request_id、campaign_id、user_id、投递/处理状态、重试次数、时间戳 |
| wallet_account | user_id、可用余额（分）、冻结余额（如启用）、更新时间 |
| wallet_ledger | id、user_id、变动金额（分）、类型、业务单号、创建时间；用户 + 类型 + 业务单号唯一，账本只追加不覆盖 |
| recharge_order | id、user_id、金额（分）、渠道、渠道交易号、状态、幂等号、创建时间；初期仅保留模型/接口约定，不产生真实充值 |
| payment_record | id、order_id、支付方式、金额（分）、状态、幂等号、支付时间 |

数据库需按查询场景增加索引，例如 merchant 的分类/区域/状态组合索引，review 的 merchant_id 与创建时间索引，订单的 user_id 与创建时间索引。唯一键规则会随“每人一单”的业务定义调整。

## 9. 前端设计方案

### 9.1 客户端范围与技术建议

- 首期按响应式 Web 设计两个入口：消费者 H5（手机优先，也可桌面浏览）和运营管理 Web（桌面优先）。如果主要用户端需要微信小程序，再单独确认是否建设小程序客户端；本稿不把 H5 自动等同于小程序。
- 前端建议 Vue 3 + TypeScript + Vite，采用 Vue Composition API 和单文件组件。该组合适合独立前端工程，并能让页面、表单、接口数据结构获得类型检查。官方文档提供 Vue + TypeScript 与 Vite 项目配置说明：[Vue TypeScript 指南](https://vuejs.org/guide/typescript/overview)、[Vite 指南](https://vite.dev/guide/)。
- 消费者端与运营端可放在同一代码仓库的两个应用目录，共用 API 类型、登录态工具、表单/提示组件和基础样式；路由、页面、权限菜单分开，避免消费者与管理功能互相耦合。
- UI 视觉建议：消费者端突出商户搜索、评分、优惠活动和抢购状态；运营端突出数据表格、筛选、状态操作、审计反馈。按手机窄屏与桌面宽屏设计断点；所有关键操作提供加载、成功、失败、空数据和无权限状态。

### 9.2 页面与导航

| 端 | 页面/路由 | 核心内容与操作 |
| --- | --- | --- |
| 消费者 H5 | 首页、商户列表、商户详情 | 搜索/筛选商户；查看评分摘要、评价列表、点赞数和优惠券活动；登录用户可点赞/取消点赞 |
| 消费者 H5 | 发布/编辑评价 | 评分、评价正文、提交结果；显示审核中/已发布/被驳回状态 |
| 消费者 H5 | 优惠券列表、活动详情 | 活动时间、库存状态、售价、规则、秒杀按钮 |
| 消费者 H5 | 抢购结果、订单列表/详情 | 显示排队中、待支付、已支付、已关闭；可按 requestId 查询结果 |
| 消费者 H5 | 我的账户、余额流水 | 显示余额和流水；充值入口显示暂未开放，或按发布配置隐藏 |
| 运营管理 Web | 登录、运营首页 | 登录、角色信息、待处理任务和关键指标 |
| 运营管理 Web | 商户管理、评价审核 | 商户资料维护；评价查询、审核、举报处理 |
| 运营管理 Web | 优惠券活动管理 | 创建/编辑/上下架、设置库存和时间、活动状态监控 |
| 运营管理 Web | 秒杀订单与系统监控 | 订单检索、失败/死信处理入口、库存对账结果、审计记录 |

### 9.3 前端模块与状态

- **应用层**：按消费者和运营端拆分路由与布局；基于角色控制导航和操作按钮。前端权限只改善交互，后端仍需对每个管理接口执行授权。
- **页面层**：页面负责组合商户、评价、优惠券、订单、钱包等业务模块；表单包含前端基础校验，服务端返回的校验错误要能定位到对应字段。
- **API 层**：集中处理 base URL、请求 ID、登录态、超时、统一错误码及响应类型；支付/下单请求附带幂等请求号。401 提示重新登录，403 显示无权访问，网络失败提供可恢复的重试操作。
- **状态管理**：只保存必要的登录用户、权限、轻量 UI 状态和临时请求状态。余额、订单、活动库存等业务事实在进入页面或用户刷新时从后端读取，不以浏览器本地缓存为准。
- **秒杀交互**：按钮按活动时间启用；提交后立即禁用重复点击并展示“处理中”，根据接口返回的 requestId 轮询结果，采用递增间隔并设置超时/停止条件；刷新页面后仍可通过用户订单或请求记录找回结果。
- **支付交互**：下单前展示金额和余额；余额不足说明原因且不宣称支付成功。支付提交中避免重复触发，最终状态以服务端订单查询结果为准。
- **安全与隐私**：HTTPS；不在前端代码、URL 或日志中暴露密钥/支付凭证；避免把余额、支付凭证或未提交评价草稿长期写入 LocalStorage。若采用 Cookie 登录，建议使用 Secure、HttpOnly、SameSite 属性并设计 CSRF 防护；具体认证方式待接口设计冻结。

### 9.4 前后端交互约定

- 页面只依赖稳定的业务 API，不直接访问 MySQL、Redis、MQ 或微信支付。
- 秒杀接口返回受理状态与 requestId；结果查询接口返回明确状态和下一步操作。客户端轮询频率受控，服务端必要时增加限流。
- 评价提交后显示服务端审核状态；摘要统计与评价列表可能短暂延迟更新，页面应从服务端刷新结果。
- 钱包余额、支付状态和充值状态均以服务端查询为准；微信支付未来接入时，浏览器支付页面的跳转/调起结果不能替代服务端异步通知。

### 10.1 测试目标与测试层次

验证消费者和运营端的关键操作可完成；秒杀不超卖、同一用户不重复下单；余额不超扣且流水与订单状态一致；缓存、消息重试和系统恢复不会造成不可修复的数据差异。测试分层如下：

| 层次 | 覆盖内容 | 建议方式 |
| --- | --- | --- |
| 前端单元/组件 | 表单校验、金额格式化、权限菜单、状态标签、轮询停止条件 | Vitest；Vue 官方脚手架支持加入 Vitest 和端到端测试配置，[Vitest 指南](https://vitest.dev/guide/) |

| 后端集成 | REST API、MySQL 事务/唯一键、Redis Lua、消息消费与重试 | 临时 MySQL 实例（可使用 Testcontainers），配合独立测试 Redis 与 RocketMQ；[Testcontainers MySQL 模块](https://java.testcontainers.org/modules/databases/mysql/) |
| 并发/性能 | 秒杀突发流量、查询热点、队列积压与消费者扩容 | 独立压测环境，按确认后的目标并发和持续时间执行；观察业务不变量、P95/P99、错误率和队列延迟 |
| 安全/恢复 | 越权、重复请求、伪造支付回调、依赖不可用、服务重启 | API 安全测试、故障注入及恢复后数据核对 |

Vue/Vite 前端工程应单独执行类型检查；Vite 的 TypeScript 转译本身不做类型检查，Vue 官方建议用 `vue-tsc` 执行检查。此项作为前端 CI 门禁，不替代运行时测试。[Vue TypeScript 指南](https://vuejs.org/guide/typescript/overview)

### 10.2 核心测试用例

| 编号 | 场景 | 关键断言 |
| --- | --- | --- |
| FE-01 | 消费者浏览商户、评价与活动 | 列表/详情、分页、空状态、错误状态与返回导航正确；窄屏页面可完成主流程 |
| FE-02 | 消费者提交/编辑评价 | 未登录需登录；字段校验生效；成功后展示服务端审核状态；非本人不能编辑/删除 |
| FE-03 | 秒杀提交与结果查询 | 连续点击只发起有效的一次请求；处理中显示正确；刷新后仍能查到最终结果 |
| FE-04 | 运营角色权限 | 普通消费者看不到运营入口；直接访问运营路由时被拦截，后端也拒绝无权 API |
| FE-05 | 评价点赞/取消点赞 | 登录用户可切换点赞状态；点赞数同步变化；重复点击/请求不会重复累计；未登录用户按登录策略处理 |
| SEC-01 | 多用户同时争抢库存 N 的活动 | 成功订单数不超过 N；数据库与 Redis 库存不为负；最终库存对账一致 |
| SEC-02 | 同一用户并发提交同一活动 | 最多创建一笔有效订单；其他请求收到重复参与/已受理结果；不重复扣库存 |
| MQ-01 | 同一秒杀消息重复投递/消费 | 订单、库存扣减和请求状态只落一次；重复消息安全确认 |
| MQ-02 | MQ 暂时不可用、发布确认超时或消费者崩溃 | 请求明确失败或进入可恢复状态；不遗留永久占用；恢复后重试/对账可完成闭环 |
| MQ-03 | RocketMQ 集群消息通道以至少 2,000 条/秒发布并消费持久化测试消息 | 发布确认成功的消息不丢失；消费者确认后可核对消息总量；记录吞吐、积压、错误率和延迟 |
| MQ-04 | 秒杀请求经过真实订单消费者持续处理 | 按确认的业务峰值压测；观测数据库事务耗时、消费延迟及队列积压；扩容消费者后积压可回落，订单和库存仍满足业务不变量 |
| PAY-01 | 余额足额支付 | 余额减少正确金额；订单变为已支付；仅有一条对应支付记录和账本流水 |
| PAY-02 | 余额不足 | 不扣余额、不写成功流水；订单保持待支付直至用户重试或超时 |
| PAY-03 | 同一订单并发/重复支付 | 最多成功扣款一次；后续请求返回已支付或幂等结果 |
| PAY-04 | 支付与订单超时关闭同时发生 | 订单只能进入已支付或已关闭之一；不得既扣款又释放库存 |
| PAY-05 | 微信通知（未来接入）重复、验签失败、金额不匹配、通知延迟 | 验签失败/金额不符不入账；重复通知只入账一次；迟到通知通过查单/补偿规则处理 |
| REV-01 | 评价新增后检查商户摘要缓存 | 评价数据持久化；摘要缓存失效或在约定时间内刷新；失败重试可恢复 |
| REV-02 | 同一用户并发点赞/取消同一评价 | 数据库最多存在一条该用户-评价关系；点赞数只按关系状态变化增减一次；重复请求结果幂等 |
| CACHE-01 | 更新商户/活动时并发读写 | 删除缓存后最终可读到新数据；短 TTL/延迟二次删除窗口后不持续返回旧值 |
| SEC-03 | 鉴权、越权、恶意输入及限流 | 非法角色不能操作运营资源；输入按规则拒绝或转义；秒杀接口限制异常高频请求 |

### 10.3 测试数据、环境与执行门槛

- 单元测试可替身外部依赖；关键集成测试必须连接真实 MySQL、Redis 和 RocketMQ 测试实例，避免只验证模拟对象。
- 使用独立测试数据库和活动数据；秒杀压测活动的数据库库存、Redis 库存及用户集合每轮重置。压测和恢复测试不得连接生产环境。
- 先做 RocketMQ 通道级 2,000 条/秒持续吞吐测试，再做包含 Redis Lua、MySQL 事务和订单消费者的端到端压测；两项结果分开记录，避免把 broker 吞吐误当成业务下单吞吐。
- 微信充值/回调在正式接入前用支付服务模拟器或微信沙箱（若适用）测试，禁止用真实资金验证自动化用例。
- 每次提交建议执行前端类型检查、后端单元测试和静态检查；合并前执行关键 API/集成测试和核心浏览器流程；版本发布前执行完整回归、并发压测和恢复演练。
- **通过标准**：所有阻断级用例通过；无库存超卖、用户重复有效订单、余额负数/重复扣款、未验签入账；订单、余额流水、库存和消息状态可核对。RocketMQ 至少 2,000 条消息/秒是已确认的最低目标；压测持续时间、端到端 P95/P99、允许错误率和 HTTP 秒杀 QPS 仍需评审确定。
- 本节是测试方案与测试用例设计，不代表已经创建或执行自动化测试。

## 11. 非功能要求（建议确认指标）

- 并发与容量：RocketMQ 至少 2,000 条消息/秒；HTTP 秒杀链路峰值、活动规模、商户和评价数据量待确认。
- 性能：商户/活动查询的目标响应时间、秒杀结果可见延迟、2,000 条/秒测试持续时间和允许的队列积压待确认。
- 可用性：Redis、MySQL、消息队列的高可用和备份策略按部署环境制定。
- 安全：HTTPS、密码安全存储、接口鉴权、运营操作审计、限流和防刷。
- 资金安全：余额变更必须来自服务端事务和账本流水；禁止客户端传入可信余额或支付结果；支付回调需验签、核对金额与商户订单，并幂等处理。
- 可观测性：统一日志与 requestId/traceId；监控 API 延迟、错误率、缓存命中率、Redis/DB 连接、队列积压、秒杀成功量及库存差异。
- 数据保护：评价内容审核、用户数据保留与删除规则待业务确认。

## 12. 部署与运行建议

- Spring Boot 应用按环境配置外置化，密钥不写入代码仓库。
- 初期采用单体 API + 独立异步消费者；按流量水平配置多实例和负载均衡。
- MySQL、Redis、RocketMQ 使用持久化及备份/恢复方案；生产环境通过健康检查、指标和告警运维。若团队已有 RabbitMQ 等稳定平台，先沿用现有平台并在架构评审时更新此处。
- 活动发布前执行库存预热及配置校验；活动结束后停止接单、处理队列余量、执行库存对账并归档活动缓存。

## 15. 多 Agent 开发协作计划

### 15.1 协作原则

- 由主协调 Agent 负责需求拆分、共用接口/数据契约、代码集成、跨模块评审和最终验收；开发 Agent 各自负责边界清楚的业务模块。
- 最多同时运行 3 个开发 Agent，另由主协调 Agent 做集成。按阶段启用前端与测试 Agent，避免多个 Agent 同时修改同一批文件。
- 开发前先读取 GitHub 仓库中的 `AGENTS.md`、README、构建配置、目录结构和现有编码规范。若已有技术选型、测试、分支或格式要求，优先沿用，不另起一套。
- 先冻结 OpenAPI/API 契约、订单状态机、表结构边界和错误码，再并行开发。共用的数据库迁移、认证配置、全局异常处理和依赖版本由主协调 Agent 管理，避免冲突。
- 每个 Agent 以独立分支或 worktree 交付；改动通过小粒度提交集成。若仓库/环境不支持 worktree，则分配明确文件所有权并错峰修改。

### 15.2 Agent 职责

| 角色 | 负责范围 | 明确边界与交付物 |
| --- | --- | --- |

| 后端 Agent B：秒杀与队列 | Redis Lua 资格与库存、每活动每用户限购一张、RocketMQ 请求处理、库存对账与待支付超时任务 | 秒杀 API/消费者、Outbox 或可靠投递设计、重试/死信/幂等、压测配置；验证消息通道至少 2,000 条/秒 |

### 15.4 并行接口与验收门槛

- **共同业务契约**：每活动每用户最多一张；评价点赞按用户+评价幂等；订单状态包括待支付/已支付/已关闭；余额以整数分记账且事务内防重复扣款；秒杀 HTTP 请求返回 requestId；MQ 集群至少 2,000 条消息/秒。
- **改动隔离**：Agent A 拥有商户/评价模块；B 拥有秒杀/队列模块；C 拥有钱包/支付模块；前端 Agent 拥有前端目录；主协调 Agent 拥有公共配置、API 规范和跨模块集成。新增公共依赖或修改公共状态机需先提交决策再合并。
- **合并门槛**：每个业务分支附测试与迁移说明；所有阻断级测试通过；库存无超卖、用户活动限购无重复、点赞计数与关系一致、余额无负数/重复扣款；MQ 通道达到 2,000 条/秒且消息可核对；全链路性能目标以确认后的 SLO 验收。
- **版本控制**：遵从仓库现有分支/PR 规则；若没有既有规范，建议短期功能分支 + 小提交 + 主协调 Agent 审查，不直接把未经集成验证的 Agent 改动合入主分支。

上述多 Agent 计划已按独立 worktree 和功能分支执行首轮开发；后续仍按相同边界推进运营写操作、缓存实现、集成测试和容量验收。RocketMQ 单机开发环境不代表已达到 2,000 条/秒目标。
